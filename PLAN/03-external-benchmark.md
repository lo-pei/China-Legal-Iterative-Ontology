# PLAN/03 · 外部本体工程实践对标

## 1. 目的与边界

本文件回答一个问题：**成熟本体工程项目在工程规范上做了哪些本项目没做的事，其中哪些能迁移而不损害本项目的纪律与自建原则。**

三条边界，先于一切结论：

1. **不导入任何现成法律本体**（AGENTS.md 禁止事项 1）。本文件引用的外部对象，除 OOPS! 的法律无关分类学部分外，均非法律本体；凡涉及法律概念切分的外部方案，一律不采纳，只登记其方法论。
2. **只取方法论与工程规范，不取内容**。对标结果是「本项目的校验器该多查什么」「本体的头信息该怎么写」，不是「本项目的概念该怎么分」。
3. **对标不构成裁定**。凡涉及法律实质判断的差异（如模块归属），本文件只登记外部存在何种分析框架，不给结论、不改变任何节点的现状。

## 4. 逐项判断说明

### 4.1 为什么 `owl:versionIRI` 是实质缺口而非形式问题

本项目 ADR-0003 的核心设计是「规则挂版本，不挂日期」：`law:抽象规范 —具有版本→ law:规范文本版本`。也就是说，**版本可被引用**是本体的第一等能力。

但本体自身没有可引用的版本节点。`PROV-0002` 登记了 `0.2.0-civil-code` 这个版本号，`law:本体` 这个 IRI 却同时指「本体」与「当前版本」。后果：

- 无法回答「`law:规则-X` 是哪一版本体下的断言」；
- 下一版发布后，旧版断言无 IRI 可回指，`PROV` 的版本登记只能靠字符串匹配；
- 与 ADR-0005「发布后只允许废弃+新增」冲突：废弃一个术语时，需要指明「在哪个版本废弃」，而版本无 IRI。

**这不是为了对齐外部标准而改，是补上本项目自身设计漏掉的一环。** 外部标准只是提供了现成形式。

### 4.2 为什么「属性缺 domain/range」不设为错误

OOPS! 把 P11 列为 Important：缺 domain/range 会导致推理不足。但本项目：

- 约束由 SHACL 承担，SHACL 不读 `rdfs:domain`；
- 部分属性（`law:溯源状态`、`law:判断状态`、`law:所属层`）**故意不写 domain**——它们被多个不相交类使用，写单一 domain 会让推理机把不该归类的节点归入该类。这是「写错比不写更糟」的典型情形。

因此判据是：**缺 domain 但补一条声明性注释（`law:有意省略domain` 或 `rdfs:comment` 说明）→ 通过；既缺又无说明 → 警告。** 不设错误级。

### 4.3 `owl:AnnotationProperty` 分流的判据

P20「误用本体注释」的实质是：把**关于本体的元数据**当成**关于实例的断言**。

判据（可操作）：**该字段描述的是「这个建模产物由谁、依据什么、何时、处于何种状态」，还是「这个法律事实是什么」。** 前者是注释，后者是数据。

- 归注释：锚定计划书条款、非法律结论、演练标记、自建声明、版本号、名称空间、中文标识符、英文注释、锚定能力问题、曾用标识符、受裁定于、受争议于、定义、示例、标注者、复核者、标注时间、指纹、覆盖范围、文件名、文件指纹、行数。
- 保持数据类型属性：事实文本、事实时间、置信度、因子编号、要件序号、要件文本、推导路径、生效日期、废止生效日、开放纹理、消极要件等（这些是实例内容）。

边界个案：`law:标注者` / `law:复核者`。它们既可视为溯源元数据（注释），也被 SHACL 用作必填约束。**SHACL 对注释属性同样生效**（`sh:path` 指向任意 IRI），故转为注释不影响门禁 2 的执行。取注释，因为它们的语义是「这条断言的可信度来自谁」，属于 §5.3 溯源链而非法律事实。

### 4.4 英文别名为什么必须机器可读

ADR-0007 §2.1 明文写：「对应关系（原英文值保留为别名，**便于外部工具互操作**）：`已验证=verified`、`候选=candidate`……」。

但实现只把这句话写进了 `law:判断状态值` 的 `rdfs:comment`。外部工具读到的是一个中文句子，取不到 `verified` 这个 token。**本体的实现没有兑现自己的 ADR。** 这是本项目内部一致性缺陷，与外部标准无关；SKOS 只是现成的承载方式。

处置：给**元层受控值**（溯源/判断/证成三轴、极性、判定结论、推理模式、规范类型）加 `skos:notation`，并把各词表声明为 `skos:ConceptScheme`。**`law:效果-*`（给付/形成/确认/责任）暂不加**——它们的英文对应在比较法上有分歧（如「给付」译 performance 还是 tender），属概念层术语选择，留待 `raw/authority/` 到位后按规范文本处理。

### 4.5 n 元关系缺口为什么不现在改

`law:法律因子` 是「因子在某案中的出现」，其极性约束为 `maxCount 1`。若同一因子实例被两个关键事实引用，而两个要件对该因子的指向相反，则无法表达。

但当前 `abox/` 为空，**没有任何实例**。按 AGENTS.md §5「升级期间不得以假设为前提推进」的同类精神，无实例支撑的结构改造属于推测性重构。处置：登记 `RSK-0008`，待首批案例标注出现该类冲突后再走 CON。**不预先改造。**

### 4.6 为什么 `rdfs:isDefinedBy` 评估后不采纳

外部清单把它列为「推荐」，前提是术语可能来自多个本体、工具需要从术语回溯到所属规范。本项目不存在这个前提：只有一个命名空间 `law:`、一个本体 `law:本体`，任一术语的 IRI 前缀已唯一确定归属。

全量添加约 614 行无差别三元组（489 类 + 125 属性），而检索能力零提升；同时每一行都不携带信息，会让 `git diff` 的信噪比变差——在本项目这种以「改了什么、为什么改」为生命线的仓库里，这是实质成本。

**这条记录的意义在于标定对标的边界**：外部清单是清单，不是命令。凡在特定前提下的建议，落到不同前提的项目上须重新判断；照抄不是学习。

### 4.7 对 `ESC-0004` 的可选参考材料（不构成建议）

`ESC-0004` 待裁定的是 `期间`、`占有`、`不可抗力` 等「事实状态性概念」的模块归属。外部存在两类可用的分析框架：

1. **OntoUML / UFO 的实体类型区分**：把「类型」与「角色（role）」「阶段（phase）」「品质（quality）」分开。若某概念是「依关系而获得、可丧失」的，它在 UFO 下属 role；若是「事物演化中的一个阶段」，属 phase。该框架的用处是把「它是不是模块里的一个类」变成「它是哪一类实体」，但不回答「归哪个模块」。
2. **BFO 的 continuant / occurrent 二分**：把「期间」这类纯时间实体与「占有」这类依赖关系成立的状态分开，可能说明它们本就不该共享同一模块位。

**明确声明**：以上只是负责人裁定时可参考的框架，本文件**不建议任何归属**，不改动 6 条待裁定概念的任何断言，也不以任何归属为前提推进后续工作。若负责人认为引入外部分类学讨论本身不合适，可整节忽略，不影响本文件其余结论。

| 不采纳 | 理由 |

## 7. 结论

本项目的**元设计、状态门禁、记录体系**在外部对标中不落下风：双轴分离、三状态轴、ESC 强制、`related` 互指与悬空依赖检查，在 OBO/LOT 生态中都属偏严的做法。

真正的差距集中在**工程规范的三处**：本体头的版本与元数据、受控词表的机器可读别名、以及**「声称可测」与「实际可执行」之间的落差**——后者最严重：20 条能力问题全部不可执行，反例测试为零，意味着 `SCHEMA.md` §8 门禁 4「已实现」这一表述只在「有代码」意义上成立，不在「已验证能拦住错误」意义上成立。

P0 项已按此判断落地，见 `ADR-0013` 与 `CON-0002`。
