# raw/authority/ · 权威材料投递说明（只读区）

> 本目录由**项目负责人**投递。系统只读，不写入、不重命名、不格式化。
> 因 `RAW` 不可变，任何勘误请**新增文件**并在文件名标注 `-勘误`，不要修改原文件。

## 为什么格式要求这么细

本项目的核心交付约束之一是「溯源链完整」：`标注值 → 标注记录 → 源文本位置 → 标注者 → 复核者 → 裁定依据`，任一环断裂即标无效（计划书 §5.2 门禁 2）。源文本位置必须能**唯一确定到条、款、项与字符区间**，否则下游无法回溯。

计划书 §阶段 2 另有一条硬约束：**系统不得自行「发明」法律概念**，遇到材料未覆盖的概念必须写 ESC 请负责人确认。因此材料覆盖范围直接决定可建模范围。

## 文件命名

```
AUTH-YYYYMMDD-NNN-规范名称.md     例：AUTH-20261115-001-民法典合同编.md
```

## 每个文件必须包含的头部元信息

```markdown
---
材料类型: 法律 | 行政法规 | 司法解释 | 部门规章 | 其他
规范名称: 中华人民共和国民法典（合同编）
公布主体: 全国人民代表大会
公布日期: 2020-05-28
生效日期: 2021-01-01
失效日期:            # 留空表示现行有效
修订说明: 无 | 第 N 次修正，修正前后条文见 AUTH-xxx
来源说明: 官方公布文本 | 负责人提供纸本扫描转录
---

## 第 XXX 条
（原文，逐款分行，不改写、不概述、不加标点）

## 第 XXX 条
...
```

## 硬性要求

1. **原文照录**：不得概述、改写、合并款项。系统要做的是把法律文本结构化，不是复述。
2. **逐条成节**：每条一个 `## 第 X 条` 小节，便于建立「条文 → 规范文本版本 → 规则」的锚点。
3. **版本信息必填**：`公布日期` 与 `生效日期` 缺一不可（ADR-0003 要求版本必须带日期，且系统不得推定）。
4. **修订必须给两版**：同一规范的修订前后文本分别投递，系统需要检验「抽象规范—文本版本」双层是否真的能承载（CQ-D07）。
5. **辅助规范一并给**：主要规范对应的司法解释条文，否则「至少一条司法解释作辅助规范」的冷启动要求无法满足。

## 首批最小集合（对应 ESC-0002）

| 项 | 数量 | 说明 |
| :--- | :--- | :--- |
| 主要规范条文 | 1 条（含款项） | 构成要件 3–5 个、含至少 1 个开放纹理要件 |
| 辅助规范条文 | ≥1 条 | 司法解释，用于解释主要规范中的开放概念 |
| 版本信息 | 1 组 | 公布日期 + 生效日期；若有修订，需前后两版 |

## 投递后系统会做什么

1. 建 `law:抽象规范` 与 `law:规范文本版本`（带日期与文本定位）。
2. 抽取构成要件与法律效果，建规则节点，`溯源状态=权威材料`。
3. 要件若含开放纹理，标 `开放纹理 true`，并在阶段 4 触发类比检索。
4. 任何「条文含义不清、要件边界无法确定」的情形 → 写 ESC，不自行解释。
