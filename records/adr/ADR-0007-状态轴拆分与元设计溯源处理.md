# ADR-0007 · 状态轴拆分与元设计断言的溯源处理

## 1. 问题（计划书中的不一致）

计划书在多处使用「状态」，但未区分三个不同的东西，直接落地会产生自相矛盾的校验规则：

1. §4.3 的 `判断状态`（verified / candidate / pending-escalation / disputed / rejected）用于**法律判断**。
2. §4.2 的 `证成状态`（已确立 / 待检验）用于**规则**，与判断状态取值不同但语义相邻。
3. §11.1 硬约束 5 写「只有 `provenance_status` / `judgment_status` 为 verified 的内容可进入确定性表示层」——但 `provenance_status` 指的是**来源类型**，来源没有「verified」这种取值；且 §4.3 又规定「verified 的来源必须是 raw/authority、ESC resolution 或测试集结论」。同一段文字里，`verified` 既是状态值又是来源条件，二者混同。

**由此产生的实际后果**：本项目第一步就要落地 `ontology/tbox/`（元模型）。元模型是系统自建设计产物，不是法律判断，也不是权威材料。按 §4.3 的字面要求，它既不能标 `verified`（系统不得把自身产物标 verified），又不能标 `candidate`（它是确定的设计，不是候选法律结论），于是**元模型无法进入任何表示层**——项目在第一步就卡死。

这属于 §一.6 允许系统自行判断的「结构性/逻辑性问题」，故由本 ADR 自行裁定，不升级。

## 2. 决策

### 2.1 三轴分离

| 轴 | 属性 | 取值 | 适用对象 |
| :--- | :--- | :--- | :--- |
| 溯源轴 | `law:溯源状态` | `溯源-权威材料` / `溯源-负责人裁定` / `溯源-测试集结论` / `溯源-自建设计` / `溯源-未溯源` | 一切进入 `ontology/` 的断言 |
| 判断轴 | `law:判断状态` | `已验证` / `候选` / `待裁定` / `有争议` / `已否定` | 仅**法律实质判断**（要件是否满足、因子是否成立、类比是否成立、归纳是否成立、冲突如何裁断、规则是否成立） |
| 证成轴 | `law:证成状态` | `已确立` / `待检验` | 仅 `law:规则` |

对应关系（原英文值保留为别名，便于外部工具互操作）：
`已验证=verified`、`候选=candidate`、`待裁定=pending-escalation`、`有争议=disputed`、`已否定=rejected`。

### 2.2 元设计豁免通道（本 ADR 的核心裁定）

**元模型构件与其断言不携带 `law:判断状态`。** 它们只携带 `law:溯源状态 溯源-自建设计`、`law:锚定计划书条款`（如 `§4.1`）与 `law:非法律结论 true`。

理由：判断状态是**不确定性**的表达装置，其存在意义是阻止未裁定的法律结论流入下游。元模型不含法律结论（它说「规则有一个法律效果槽位」，不说「本案价款请求权成立」），对其施加判断状态只会产生空洞标记，并诱导后续把「元设计」与「法律判断」混为一谈。

### 2.3 门禁表（唯一权威，供 `tools/validate` 与 `tools/sync` 共用）

| 组合 | 可入确定性表示层 | Wiki | RAG 检索 |
| :--- | :--- | :--- | :--- |
| 判断状态=已验证 且 溯源状态∈{权威材料, 负责人裁定, 测试集结论} | 是 | 是 | 可作确定答案 |
| 判断状态=候选 | 否 | 是（标「候选」） | 可召回，答案须标「候选」 |
| 判断状态=待裁定 | 否 | 是（红标「待裁定」） | 不得作答案，仅作「待裁定事项」提示 |
| 判断状态=有争议 | 否 | 否（仅 RSK/ESC 内） | 不返回 |
| 判断状态=已否定 | 否 | 否（记录留存追溯） | 不返回 |
| 无判断状态 且 溯源状态=自建设计 且 非法律结论=true | 是（标注「元设计」） | 是 | 可返回，须标「元设计/非法律结论」 |
| 溯源状态=未溯源 | 否 | 否 | 不返回 |

### 2.4 跨轴不变式（可机器校验）

- `证成状态=已确立` ⇒ `判断状态=已验证` 且 `溯源状态∈{权威材料, 负责人裁定, 测试集结论}`。
- `证成状态=待检验` ⇒ `判断状态∈{候选, 待裁定, 有争议, 已否定}`。
- `判断状态=已验证` ⇒ `溯源状态≠自建设计`（严格禁止系统自证，§4.3 末句）。
- `判断状态=待裁定` ⇒ 必须存在至少一条 `status: open` 的 ESC 指向该节点（E-ESC-01）。
- `判断状态=有争议` ⇒ 必须存在至少一条未关闭 RSK 指向该节点（E-RSK-01）。

## 3. 放弃方案与代价

| 放弃方案 | 放弃原因 | 代价 |
| :--- | :--- | :--- |
| 严格按字面，元模型也走 ESC 逐条裁定 | 会把「规则有构成要件槽位」这类工程判断变成负责人的裁定负担，属于典型过度升级（§11.5 第 5 步明令审查此现象） | 负责人时间被工程细节耗尽；ESC 队列噪声掩盖真实法律争议 |
| 元模型直接标 `verified` | 违反 §4.3「系统不得将自身推理产物直接标为 verified」 | 破坏整个门禁的可信度，铁律失效 |
| 取消 `证成状态`，只用 `判断状态` | 证成状态是「规则作为规范主张的确立程度」，判断状态是「本次判断的认识论状态」；候选规则在被否定后仍需保留「曾为待检验规则」的证成轨迹 | 归纳检验阶段无法表达「规则被降级但仍存在」，只能删除，丢失演进史 |

## 4. 生效约束

- `SCHEMA.md` §5 记录本门禁表的等价副本；两处不一致时以本 ADR 为准，并立即修 `SCHEMA.md`。
- `tools/validate` 必须实现 §2.4 全部五条不变式，任一不满足即非零退出。
- 新增状态值需 CON + ADR；不得在 ABox 内使用未登记的状态值。

## 5. 复审触发条件

- 若出现「元设计断言被用于法律结论」（例如元模型中的示例规则被 RAG 当法条返回）→ 立即复审豁免通道。
- 阶段 5 若 `非法律结论=true` 的条目 > 总条目 30% → 复审是否应把元设计单独装入 `ontology/` 之外的命名空间（如 `mcl-meta:`），以物理隔离代替标记隔离。
