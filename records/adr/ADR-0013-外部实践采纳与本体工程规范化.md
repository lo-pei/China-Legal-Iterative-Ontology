# ADR-0013 · 外部实践采纳与本体工程规范化

## 1. 背景

负责人 2026-11-10 指令：「学习 GitHub 上有关 ontology 的知识对本项目进行改进，但要学习优秀作品，不要降低本项目质量。」该指令构成对本轮改动的授权，但授权范围须由本 ADR 自我限定，否则「改进」会成为绕过纪律的口子。

对标过程与逐项判断见 `PLAN/03-external-benchmark.md`。本 ADR 只记录**采纳了什么、边界在哪、为什么这么判断**。

三项前置事实（均有实测证据，不是推断）：

1. `ontology/` 中 `owl:AnnotationProperty` 数量为 **0**，`owl:DatatypeProperty` 为 **77**——元数据字段与实例数据字段混用同一属性类别。
2. 本体头**无 `owl:versionIRI`**，只有 `owl:versionInfo` 字符串与自定义 `law:本体版本`。
3. `PLAN/01-scope-freeze.md` 中 20 条能力问题全部只有自然语言验收判据；`tools/validate/fixtures/` 只有正例，无反例。

## 2. 决策

采纳 P0 八项，全部为结构性改动，无一项含法律实质判断。

### 2.1 版本标识（补 ADR-0003 的漏项）

- `law:本体` 增 `owl:versionIRI <https://ontology.law-cn.internal/mcl/0.2.0>`。
- 版本 IRI 用**目录式**（`/mcl/0.2.0`）而非片段式（`/mcl#0.2.0`）。理由：片段是同一实体的片段，不能标识「另一个实体」；版本需要是独立可引用的实体。
- 术语 IRI 保持 `mcl#` 基础命名空间不变（ADR-0005 不动）。
- 后续版本按 `owl:priorVersion` 指向前一版本 IRI。本条在 `0.3.0` 首次发布时生效，当前 `0.2.0` 无前版。

### 2.2 本体头元数据

补 `vann:preferredNamespacePrefix` `"law"`、`vann:preferredNamespaceUri`、`dcterms:title` / `description` / `created` / `modified` / `language`。

**不补** `dcterms:license` / `creator` / `publisher`：本体未发布，命名空间为 `.internal`，此时声明许可无实际后果，只会制造无法消除的门禁噪声。三者列为发布前置项，写入 §5.3。

### 2.3 元数据属性分流（回应 OOPS P20）

判据：**该字段描述「这个建模产物由谁、依据什么、何时、处于何种状态」→ 注释属性；描述「这个法律事实是什么」→ 数据类型属性。**

转为 `owl:AnnotationProperty`（37 个，逐文件清单见 `CON-0002` §2.1）。判据不变，执行时按同一判据覆盖了 `70-concept-metadata.ttl` 的 10 个清单登记字段与 `30`/`40` 各 1 个溯源字段。

**关键核对**：`law:标注者` / `law:复核者` 转为注释属性后，SHACL 的 `sh:minCount 1` 仍然生效（`sh:path` 可指向任意 IRI，属性类别不影响 SHACL 判定）。门禁 2「溯源链完整」的执行力不变，`E-KF-05` / `E-KF-06` 仍会报出。

### 2.4 受控词表机器可读别名（补 ADR-0007 §2.1 的漏项）

- 各词表声明 `skos:ConceptScheme`；词表值为 `skos:Concept` + `skos:inScheme`。
- 元层受控值增 `skos:notation` 承载英文 token：三状态轴、极性、判定结论、推理模式、规范类型、废止类型。
- **`law:效果-*` 不加**：给付/形成/确认/责任的英文对应在比较法上有分歧，属概念层术语选择，留待规范原文到位。
- `rdfs:label` 全部保留不动，`skos:prefLabel` 不重复添加（避免同义双写）。

### 2.5 术语卫生检查（新增 5 条校验）

| 码 | 级 | 内容 |
| :--- | :--- | :--- |
| `E-TERM-01` | E | 同一 IRI 同时声明为 `owl:ObjectProperty` 与 `owl:DatatypeProperty`（属性类型冲突，会导致 SHACL 与推理行为不确定） |
| `E-TERM-02` | E | 同一 IRI 既是类又是属性（punning 冲突，除 OWL 2 DL 允许的有限情形外禁止） |
| `W-TERM-03` | W | 类或属性缺 `rdfs:label` |
| `W-TERM-04` | W | 类缺 `rdfs:comment` |
| `W-TERM-05` | W | 属性既无 `rdfs:domain` 也无 `rdfs:range`，且未以注释声明「有意省略」 |

`W-TERM-05` 的依据见 `PLAN/03` §4.2：本项目约束由 SHACL 承担，缺 domain 未必是缺陷；但**有意省略与疏忽遗漏必须可区分**，故用注释作为区分手段。判据是存在 `rdfs:comment` 中包含「有意省略」四字，或 `law:有意省略domain true`。

### 2.6 反例测试集

- 新增 `tools/validate/fixtures/negative/*.ttl`，每个文件对应一个**应当被拦住的错误**，文件头注释写明预期错误码。
- `validate.py --negative` 逐文件独立加载（**不得并入主校验图**，否则会污染生产态基线），检查预期错误码是否真的被报出，输出检出率 `N/M`，未检出则非零退出。
- **能力边界**：该指标测的是「校验器对已知错误的检出能力」，**不是**「标注者错误率」，不得外推替代 `SCHEMA.md` §8 门禁 3 的抽样复核，也不得用于填充 `META` 的「错误注入检出率」指标。此边界写入 `SCHEMA.md` §8 备注。

### 2.7 能力问题执行器

- `tools/test/cq/*.rq`（SPARQL 查询）+ `tools/test/cq/manifest.tsv`（CQ 编号 → 查询文件 → 期望结果 → 数据集）。
- `tools/test/run_cq.py` 执行并输出通过/失败与需求—证据矩阵。
- 首批 3 条：`CQ-D02`（要件必填字段齐全且开放纹理为显式布尔）、`CQ-I02`（候选规则与规则同构）、`CQ-M03`（无「已验证 + 自建设计」组合）。
- 默认数据集为 `tools/validate/fixtures/STRUCT-DRYRUN.ttl`（当前 `abox/` 为空，唯一有数据的图）。真实语料到位后切换。
- 未实现的 17 条在 `manifest.tsv` 中显式标 `未实现`，**不得留空**——留空会被误读为已覆盖。

**补记（追加于实现之后，非 §2.7 原案）**：初版执行器只证明了「查询在干净数据上返回 0 行」，而这与「查询恒假」在报告上无法区分——正是本 ADR 在批评的自欺。补 `tools/test/cq/bad/*.ttl`（每条已实现查询一个反例样本）与 `run_cq.py --selftest`：反例须令查询返回 ≥1 行，否则该查询无权充当验收判据。当前检出 3/3。边界同 §2.6：该指标证明**查询能检出已知违规**，不证明**违规已被穷尽**，也不得据此上调 CQ 覆盖率。详见 `LOG-20261110-008`。

## 3. 理由

1. **三项都是「本项目自己的设计没有落地」，不是「外部要求本项目改」。** 版本可引用是 ADR-0003 的前提；英文别名可机器读是 ADR-0007 §2.1 的明文；「可回测」是 `PLAN/01` 对每条 CQ 的分类。对外部标准的引用只是提供了现成实现形式，不能据此说本项目在「迎合外部」。
2. **反例测试是唯一能把「门禁 4 已实现」从声明变成证据的手段。** 当前 `validate.py` 有 700 行代码、SHACL 有 271 行形状，从未被喂过错误数据。没有反例的校验器无法自证其有效性。
3. **改动全部落在结构层**（AGENTS.md §4.1）：属性的类别、头的字段、校验的覆盖面、测试的存在与否。判据「结论会不会改变当事人的权利义务」——全部为「不会」。

## 4. 放弃方案与代价

| 放弃方案 | 放弃原因 | 代价 |
| :--- | :--- | :--- |
| 给全部术语补 `rdfs:isDefinedBy` | 单命名空间下该字段是重复信息（IRI 前缀已唯一确定归属），全量添加约 614 行无差别断言，检索能力零提升 | 多本体互操作场景下需重新评估 |
| 引入 ROBOT / ODK 跑 `report` / `verify` | 需 JVM + OWL API，与 ADR-0008「纯 Python、零额外依赖」冲突；且 ROBOT 以 OBO 惯例为前提（ID 形如 `GO:0000001`），与中文 IRI 不兼容 | 需自行实现其检查项（本项目检查项少，成本可接受）；无法获得 ROBOT 的 HTML 报告与 CI 集成 |
| 引入 OWL 2 DL profile 校验 | 本项目大量使用「类作为属性值」（`law:所属层 law:规范层`），在该 profile 下会大面积报错；修掉它们的代价大于收益 | 无法在语言层证明一致性，只能做结构检查（已在 SCHEMA §11 登记） |
| 一次性把 20 条 CQ 全部落为 SPARQL | 其中 12 条依赖案例与标注数据（`abox/` 为空），现在写查询只能对空结果断言「通过」，等价于伪造可测性 | 只能覆盖 3 条结构类 CQ；其余显式标「未实现」，可测性等级相应下调 |
| 把 `dcterms:license` 设为必填门禁 | 未发布本体无许可需求；强制填入会迫使我替负责人做许可选择（越权） | 发布前需补一次元数据（已列为发布前置项） |
| 按 OOPS! 全量 41 项建检查 | 其中 7 项依赖 DL 推理、4 项属策略判断，无推理机时强做会产生误报，误报会训练出「忽略警告」的习惯，比不检查更坏 | 只覆盖可可靠判定的子集 |
| 现在就做 n 元极性改造（`PLAN/03` §4.5） | `abox/` 无实例，无证据表明该冲突真实发生；推测性重构违反「不以假设为前提推进」 | 缺口保留，登记 `RSK-0008` |

## 5. 生效约束

### 5.1 对后续改动的约束

1. 新增属性时须在 `owl:ObjectProperty` / `owl:DatatypeProperty` / `owl:AnnotationProperty` 三者中显式选一，判据见 §2.3。不得默认写 `DatatypeProperty`。
2. 新增元层受控值须同时给 `rdfs:label`、`rdfs:comment`、`skos:inScheme`，并在能确定英文 token 时给 `skos:notation`。
3. 新增反例样本必须写明预期错误码；预期错误码与实际不符时，先判断是样本写错还是校验器漏检，**不得直接改预期以迁就实现**。
4. 修改 `tools/validate/shapes.ttl` 或新增校验码时，若该码被反例样本覆盖，须同步更新样本。

### 5.2 对既有记录的约束

1. `SCHEMA.md` §5 门禁表、§7 工具登记、§8 门禁状态、§9 借鉴登记须同步更新；三处与本节不一致时以本节为准。
2. `tools/validate` 新增的错误码须在 `SCHEMA.md` §12 登记，否则视为未定义码。

### 5.3 发布前置项（未完成，明确挂账）

以下在本体真正对外发布前必须完成，当前不做：

- `dcterms:license`、`creator`、`publisher`；
- 命名空间从 `.internal` 迁移到可解析 IRI 的策略（涉及 ADR-0005，须新 ADR，不得在本 ADR 内夹带）；
- 内容协商与 `owl:imports` 可达性。

## 6. 复审触发条件

1. `abox/` 首次出现实例后，重跑 `--negative` 与 CQ 执行器，评估覆盖是否仍成立。
2. 若 `W-TERM-05` 的「有意省略」注释超过属性总数 50%，复审该警告是否有信息量（可能是判据过宽）。
3. 若反例样本连续两轮出现「校验器漏检」，复审 `validate.py` 与 `shapes.ttl` 的职责分工是否已失效。
4. 引入任何 OWL 推理机时，复审 §2.3 的属性分流是否需要回退（推理机对注释与数据属性的处理不同）。
