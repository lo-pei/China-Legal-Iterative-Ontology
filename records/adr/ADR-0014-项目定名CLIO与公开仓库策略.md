# ADR-0014 · 项目定名 CLIO 与公开仓库策略

## 1. 背景

负责人 2026-11-10 指令：「给项目文件重命名，China Legal Iterative Ontology（CLIO），并推送 GitHub
`https://github.com/lo-pei/China-Legal-Iterative-Ontology`」。

经确认，重命名范围限定为**文档与文件名**，不含命名空间 IRI；推送范围为**重命名 + 现有未提交变更**，一并推送。

本 ADR 处理一个此前未决的问题：项目对外身份（名称、仓库位置）与本体技术标识（命名空间 IRI）
是否需要同时变更。答案是**不需要同时变更**，但必须把不同步的理由与代价写下来，否则「内部名」会成为长期债。

## 2. 决策

### 2.1 项目名

对外名称定为 **CLIO · China Legal Iterative Ontology**，中文表述「中国法律迭代本体」。

*Iterative* 描述建设方式而非版本序列：每轮闭环产出一条 `ITER`、一次假设检验与一次自我修正，
本体随裁定到达而增补。名称因此同时是方法声明——本项目拒绝「一次写全」的交付模型。

### 2.2 改名波及面与处置

| 对象 | 处置 | 理由 |
| :--- | :--- | :--- |
| `README.md` 标题与首段 | 改为 CLIO 并增「代号释义」引述块 | 对外第一入口，须与新名一致 |
| `法律本体自建项目 · 最终版计划书.md` | `git mv` 为 `CLIO · 最终版计划书.md` | 计划书是治理文件，文件名即引用标识 |
| `README.md` 中对计划书的引用 | 同步改路径 | 悬空引用属结构缺陷，`validate` 不查但属 I 级 |
| `tools/vis/render.py` 页面标题（2 处） | 改为 `CLIO · 结构与健康度` | 生成源，改后重跑覆盖投影 |
| `vis/index.html` | **不手改**，由 `render.py` 重生成 | 投影不可手改（`AGENTS.md` 禁止事项 3） |
| `records/` 内历史记录的旧称 | **不改** | 已闭合记录不可删改（`AGENTS.md` 禁止事项 7）；历史记录的是当时的名称事实 |
| 命名空间 IRI `https://ontology.law-cn.internal/mcl#` | **本次不动** | 见 §2.3 |

`INDEX.md`、`SCHEMA.md`、`AGENTS.md` 正文未出现旧项目名（仅出现「现成法律本体」这一限制语，非项目名），
故无需改动；已在 `LOG-20261110-009` 中记录核验结果，以免被误读为遗漏。

### 2.3 命名空间 IRI 不随项目改名迁移（关键判断）

`https://ontology.law-cn.internal/mcl#` 出现在 **482 个文件、930 处**，其中 445 处位于 `wiki/` 投影。

不迁移的理由有三条，按强度排序：

1. **改名与改 IRI 是两类不同事件**。项目名是人的称呼，IRI 是图内实体的身份。
   改称呼不影响任何三元组的主语；改 IRI 则使全部 445 个概念、77 个数据属性、24 个构件类
   在外部引用层面变成**另一批实体**。后者是破坏性变更，须独立评估，不得夹带在改名里。
2. **`ADR-0013 §5.3` 已明文挂账**：命名空间从 `.internal` 迁移须新 ADR，且「不得在本 ADR 内夹带」。
   在改名 ADR 里顺手改 IRI，正是该条要防的操作。
3. **`.internal` 本就不可解析**，其缺陷在于「不可解引用」，与项目叫不叫 CLIO 无关。
   只换域名前缀（`law-cn.internal` → 某 CLIO 域名）并不解决不可解引用，反而制造一次无收益的指纹变动与
   445 份投影重生成。真正需要的是**一次带策略的迁移**（含 `owl:priorVersion`、旧 IRI 保留期、
   重定向或 `sameAs` 桥接），那是独立 ADR 的工作量。

**代价（明示）**：项目对外叫 CLIO，本体 IRI 仍是 `law-cn.internal`，二者字面不一致，会让外部读者困惑。
缓解措施：在 `README.md` 的「命名空间」说明处写明「术语 IRI 沿用 `mcl#`，待发布迁移 ADR 处理」，
并把该迁移登记为 `RSK-0009`。

### 2.4 公开仓库

远程：`https://github.com/lo-pei/China-Legal-Iterative-Ontology`（公开，默认分支 `main`）。
本地当前分支 `master`，推送时改名为 `main`，避免远程出现双默认分支。

本地分支名 `master` → `main`：纯命名调整，无历史重写，不违反「禁止删除已关闭记录」等纪律。

## 3. 理由

- **公开是策略问题，不是技术问题**。本项目当前最有价值的产出是**纪律本身的可验证性**
  （校验器会拦、CQ 能判、升级机制真的停住了），而这类产出的可信度依赖「别人能跑」。
  公开仓库让「跑 `validate.py --negative` 得 6/6」从声明变成可复核事实。
- **公开的时机风险已评估**。仓库当前无 `raw/authority/` 内容（三份 README 仅为投递说明，无当事人信息）、
  无判决书原文、无个人信息。不存在公开即泄密的问题。
- **不出售「完成度」**。README 首屏即写明规则层与案例层为零及其原因，避免把「纪律性暂停」误读为「项目完成」。

## 4. 放弃方案与代价

| 方案 | 放弃理由 |
| :--- | :--- |
| 同时迁移命名空间 IRI | 破坏性变更夹带在改名中；违反 `ADR-0013 §5.3`；不解决不可解引用；445 份投影重生成无收益 |
| 只改 README 标题，不动计划书文件名 | 计划书是治理文件，文件名带旧项目名会成为长期不一致源；`git mv` 成本极低 |
| 不建独立 ADR，仅写 LOG | 这是「命名与发布」的选择，含放弃方案，属 ADR 范畴；只写 LOG 会使后续接手者不知 `law-cn.internal` 为何未随名而改 |
| 保持仓库私有 | 与「以可验证性建立可信度」的目标冲突；当前内容无保密需要 |

## 5. 生效约束

1. **术语 IRI 冻结**：在发布迁移 ADR 生效前，不得以「与新名不一致」为由修改任何 IRI。
2. **不得手改投影**：改名引发的投影差异只能由 `tools/sync/sync.py`、`tools/vis/render.py` 重生成产生。
3. **历史记录不改称**：`LOG-20261110-001` 等已闭合记录中的旧称保持原样；若需说明，追加而非改写。
4. **发布前置项未完成**：`dcterms:license` / `creator` / `publisher` 仍缺（`ADR-0013 §5.3`）。
   公开仓库不等于本体发布；在补 license 前，不得在 `ontology/` 中声明任何许可，
   也不得对外宣称「本体已发布可用」。该缺口登记为 `RSK-0009`。
5. 后续新增文档不得再使用旧项目名；`validate` 未覆盖此项，属人工门禁。

## 6. 复审触发条件

- 迁移命名空间的 ADR 起草时（届时须同步处理 `owl:priorVersion` 与旧 IRI 保留期）。
- 首次在 `README` 之外（如论文、对外文档）引用项目名时。
- 若有外部方开始以 `mcl#` IRI 引用本项目概念——届时 `.internal` 不可解析从「内部缺陷」升级为「对外断链」，
  迁移优先级须立即提升。
