# LOG-20261110-009 · 项目定名 CLIO 与首次公开推送

## 1. 做了什么

1. **定名**：对外名称改为 `CLIO · China Legal Iterative Ontology`，中文「中国法律迭代本体」。
2. **文件改名**：`git mv 法律本体自建项目 · 最终版计划书.md → CLIO · 最终版计划书.md`。
   用 `git mv` 而非删除+新建，保留文件历史。
3. **文档改名**：`README.md` 标题与首段；新增「代号释义」引述块，说明 *Iterative* 指建设方式（每轮闭环一条 `ITER`）
   而非版本序列。
4. **生成源改名**：`tools/vis/render.py` 的 `<title>` 与 `<h1>` 两处改为 `CLIO · 结构与健康度`。
5. **投影重生成**：`vis/index.html` **未手改**，由 `python tools/vis/render.py` 覆盖生成（31580 字节）。
6. **命名空间核验**：`https://ontology.law-cn.internal/mcl#` 出现在 **482 个文件 / 930 处**，
   其中 445 处位于 `wiki/` 投影。判定**本次不迁移**，理由与代价写入 `ADR-0014 §2.3`。
7. **补记录**：`ADR-0014`（定名与公开策略）、`RSK-0009`（定名与命名空间不一致、发布前置项未完成）。
8. **公开前检查**：`raw/` 仅三份投递说明 README，无规范原文、无判决书、无个人信息；
   `raw/testset/` 为空。确认公开不涉及泄密。
9. **推送**：远程 `https://github.com/lo-pei/China-Legal-Iterative-Ontology`，本地分支 `master` → `main`。
10. **途中发现并修复阻断性缺陷（一）**：首次 `git add -A` 失败于 `records/con/` 下两个文件，
    根因是目录名 `con` 为 Windows 保留设备名（`CON`）。已改名 `records/concept/`，内容逐字节不变
    （SHA-256 迁移前后一致），记录编号不变，4 处路径引用已同步。详见 `ADR-0015`。
11. **推送后做全新克隆验证**，发现第二处缺陷：克隆侧校验报 `W-TBOX-DRIFT`
    （实测 `b3fb0e97…` vs 登记 `faa7773f…`）。根因是事实源换行状态混杂＋`core.autocrlf=true`
    在检出时把 LF 转 CRLF，而指纹按原始字节计算。已统一事实源为 LF、新增 `.gitattributes`
    锁定检出行为、重算指纹并登记 `PROV-0004`（全量 `22ff6bd9…`、概念层 `46e380f6…`）。详见 `ADR-0016`。
12. **克隆复验**：重新克隆后执行三项门禁，全部与本地一致，`README` 的「0 警告」声明现已开箱可复现。

## 2. 为什么这样做

### 2.1 为什么不在改名时顺手改 IRI（本轮最重要的判断）

表面看「重命名为 CLIO」似乎包含换掉 `law-cn.internal`，但二者是不同性质的事件：

- **项目名是人的称呼**，改它不动任何三元组的主语。风险为零。
- **IRI 是图内实体的身份**，改它使 445 个概念、77 个数据属性、24 个构件类在外部引用层面变成另一批实体。
  这是破坏性变更：任何已有的引用（含本项目自己的 `.rq` 查询、`shapes.ttl`、反例样本）全部失效。

`ADR-0013 §5.3` 已把「命名空间迁移」列为发布前置项，并明文规定「须新 ADR，不得在本 ADR 内夹带」。
本轮若顺手改了，恰好绕过这条自己定的约束。**约束的价值在于它拦住自己想偷懒的那一次。**

更关键的是：**换前缀不解决问题**。旧 IRI 的病根是 `.internal` 不可解引用；把 `law-cn.internal`
换成某个 CLIO 域名，若不配套内容协商与文件托管，新 IRI 一样不可解析。真正的迁移是一次带策略的工程
（旧 IRI 保留期 + `owl:priorVersion` + 桥接 + 445 份投影重生成 + 指纹重登记），不是字符串替换。

### 2.2 为什么公开

本项目可交付的东西里，「已建成的本体」占比很小（规则层案例层为零），「可验证的纪律」占比很大：
校验器会拦（反例 6/6）、CQ 能判（3/3 自检）、升级机制真的停住了（4 条 `open` ESC 未被绕过）。
后者只有在别人能自己跑一遍时才是证据，否则仍是声明。公开仓库把「跑 `--negative` 得 6/6」变成可复核事实。

### 2.3 为什么不改历史记录里的旧称

`LOG-20261110-001` 等已闭合记录中的「通读 `法律本体自建项目 · 最终版计划书.md`」保持原样。
理由：记录记的是**当时的事实**（当时文件确实叫那个名字）。改写历史记录会使「记录先于实现」
这一条纪律失去可信度——如果记录可以为了整洁而被追改，它就不再是凭证。
旧称与新名的不一致由本 LOG 与新 ADR 解释，不靠篡改历史消解。

### 2.4 为什么把分支从 master 改为 main

远程仓库默认分支为 `main`（GitHub 新建仓库默认）。本地为 `master`。若不统一，
推送后会出现 `main`（空）与 `master` 两个分支，默认分支指向空分支，克隆者拿到空仓库。
改名不重写历史，仅调整引用名，`git branch -m master main` 即可。
