# ITER-0001 · 自举轮（从零到可校验的元设计）

**本轮闭环定义**：读计划书 → 判定初始态 → 建目录与记录体系 → 元设计 → tbox 落地 → 校验器 → 投影 → 记录归档。
**闭环是否完整**：完整（有输入、有产出、有机器校验、有记录）。**但阶段验收未完成**：P0 卡 `ESC-0001`，P1 待负责人确认，故本轮不产生 `ACC`。

## 1. 本轮隐含假设（反推）

| 编号 | 假设 | 来源 |
| :--- | :--- | :--- |
| H1 | 五模块（主体/行为/规范/关系/效果）足以承载全部节点类型，因子、案例、适用节点也可挂模块 | 计划书 §4.1 + §阶段 6 硬规则 1「新增概念必须声明五模块归属」 |
| H2 | 一套「判断状态」同时表达「来源是否可信」与「判断是否确定」 | 计划书 §4.3 与 §11.1 硬约束 5 的措辞 |
| H3 | 候选规则应与成文规则并列为独立类，各自建槽位 | 计划书 §4.2「候选规则与成文规则同构」的直读 |
| H4 | 中文标识符（中文 IRI 局部名）在 rdflib / pyshacl 工具链下可用 | ADR-0005 的前提 |
| H5 | SHACL + 自研校验足以覆盖 §5.2 门禁 4「一致性检验」 | 计划书 §阶段 3「自定义 RDF 词汇表 + SHACL」 |
| H6 | 无权威材料时，结构演练可替代真实规则形式化，使阶段 1 得以关闭 | 推进压力下的默认想法 |

## 2. 证据与逐条裁定

### H1 → **证伪**

证据：
- 写作 `ADR-0006` 时发现「因子挂哪个模块」不可判定。具体反例：「及时提出异议」既可解释为行为（提出异议这个动作），也可解释为关系（对对待给付的争议状态）。这不是标注者水平问题，是该节点类型本身没有模块归属。
- 若强行归类，分类分歧会伪装成法律分歧，进而触发大量本不该有的 ESC（与 `AGENTS.md` §4.3 防过度升级冲突）。

裁定：**证伪**。处置：`ADR-0006` 引入两条正交轴——模块管法律概念（类），层管建模构件（个体）。构件不受模块归属约束。

### H2 → **证伪**

证据：
- 计划书 §4.3 写「`verified` 的来源必须是 raw/authority、ESC resolution 或测试集结论」，同段又说「只有 provenance_status / judgment_status 为 verified 的内容可进入确定性层」。同一段里 `verified` 既是**状态值**又是**来源条件**。
- 落地后果：`ontology/tbox/` 是系统自建设计，按字面既不能标 `verified`（禁止自证），也不该标 `candidate`（它不是候选法律结论）。元模型无法获得任何状态 → 第一步卡死。

裁定：**证伪**。处置：`ADR-0007` 拆三轴（溯源 / 判断 / 证成），并开「元设计豁免通道」（无判断状态 + `非法律结论 true`）。按 §一.6，此为结构性/逻辑性问题，系统自行裁定，未开 ESC。

### H3 → **证伪**

证据：
- 若建两个独立类，则「同构」只能靠两套手写 SHACL 形状维持；一旦规则形状变更，候选规则形状会漂移，而这种漂移不会被任何校验发现（因为两个类各自自洽）。
- 反向验证：改为 `候选规则 rdfs:subClassOf 规则` 后，pyshacl 以 `inference='rdfs'` 执行时自动套用规则形状，`LOG-20261110-004` 的运行结果显示演练中的候选规则通过了全部六条规则必填约束，无需第二套形状。

裁定：**证伪**。处置：`ADR-0006`/tbox 中候选规则为规则的子类，差异只在 `证成状态=待检验`。

### H4 → **支持**

证据：`LOG-20261110-004` §2 三项实测全部通过（Turtle 解析、图遍历/IRI 索引、SHACL 校验）。证据文件：`ontology/tbox/*.ttl`、`tools/validate/validate.py`、`tools/validate/shapes.ttl`。

裁定：**支持**。限制：Protégé / Neo4j / Jena **未测**，不得外推。已记 `RSK-0004`。

### H5 → **部分支持**

证据：
- SHACL 覆盖了局部基数与取值（规则 6 项、要件 4 项、关键事实 6 项等），且在演练中确实生效。
- 但以下约束 SHACL 表达不了，必须自研：待裁定节点 ↔ open ESC 的对应、`related` 互指、版本区间不重叠、因子—关键事实—要件链连通、索引升级队列完整性。这些已在 `validate.py` 实现。
- 仍缺：OWL DL 级可满足性（需推理机，`ADR-0008` 已作放弃方案）。所以「门禁 4」只能做到结构性可满足，做不到 DL 级证明。

裁定：**部分支持**。处置：无需新 ADR（`ADR-0008` §3 已登记该缺口），但在 `SCHEMA.md` §11 明示缺口。

### H6 → **证伪**

证据：
- 演练样本能验证「元设计能否承载结构」，不能验证「某类合同的要件应划几个、哪个算开放纹理」。后者是语义切分，属法律实质判断。
- 若以演练关闭阶段 1，则 `PLAN/02` §7 的结论会被误读为「元设计已通过真实规则检验」，而实际上第一次真实形式化很可能暴露要件粒度问题。

裁定：**证伪**。处置：阶段 1 保持「元设计完成、待真实压测」状态；`PLAN/02` §7 明确写「未验证部分」；本轮不写 `ACC`。

## 4. 升级机制自审（§11.5 第 5 步）

**本轮 ESC 数**：3（2 blocking + 1 non-blocking）。全部为真正需要负责人裁定的问题：子领域归属、材料投递、复核角色。

### 过度升级审查（本可自行判断却升级了？）

识别出 2 项候选，均**未**升级，判断正确：

| 候选事项 | 是否应升级 | 理由 |
| :--- | :--- | :--- |
| 目录树缺 `PLAN/` `vis/`、测试集引用记录落点冲突 | 否 | 结构性缺陷，§一.6 授权自行判断；已由 ADR-0001 记录理由与代价 |
| 元设计断言是否需要判断状态 | 否 | 逻辑/结构问题，不涉及法律评价；已由 ADR-0007 裁定 |

若两项都升级，ESC 会变成 5 条，其中 2 条是工程细节——这会淹没真正的法律争议（§11.5 明确要求审查此现象）。

### 漏升级审查（应升级却自行判断了？）

逐项检查本轮所有「给出结论」的动作：

| 动作 | 是否含法律实质判断 | 结论 |
| :--- | :--- | :--- |
| 定义五模块的语义范围（主体=谁…） | 元设计分类，不含具体法律概念归属 | 无漏升级 |
| 演练样本中「要件 1–4」的划分 | **潜在风险点**：若被当作某类合同的真实要件主张，即属越界 | 已三重隔离：`演练-` 前缀、`非法律结论 true`、禁入 wiki/RAG（`sync.py` 只读 abox，fixture 不在 abox） |
| 「但书型例外建为消极要件、外部废止建为废止条件」 | 元设计规则，说明的是**表示方式**而非**某条规范的性质** | 无漏升级 |
| 「首批因子 30–50 个」 | 数量指标，来自计划书 | 无漏升级 |

**结论**：本轮无漏升级。唯一风险点是演练样本被误读，已通过命名与管线隔离处理；此风险登记于 `META-0001` §2 供下轮复查。

### 升级判据的边界调整

本轮实践中形成一条可操作口径，建议写入 `AGENTS.md`（已在 §4.1/4.2 体现）：

> 判断「这是不是法律判断」，问一句：**结论会不会改变当事人的权利义务？** 会 → 必须升级；不会（只改变图的结构）→ 自行判断。
