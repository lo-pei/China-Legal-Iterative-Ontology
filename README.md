## 1. 项目概览

CLIO 是一个**自我建构**的中国民事法律本体。它不解一道题，而是建立一套能把法律推理过程写进图里、并可被机器校验的结构。

大多数法律知识图谱止步于「法条—概念—案例」的三元关联。CLIO 的差异在于：它要求**推理形态本身**成为可校验的对象。演绎、类比、归纳三种推理方式在同一图层中共存，各自带上自己的合法性条件；一条规则缺了法定效果、一个概念同时挂进两个模块、一个节点自称「已验证」却源于系统自身设计——这些都不是靠人工审阅发现，而是由校验器拦截。

> 项目代号 **CLIO**。名称中的 *Iterative* 指的是建设方式：每一轮闭环产出一条 `ITER`、一次假设检验与一次自我修正，本体随裁定到达而增补，而非一次性写全。**「迭代」是方法约束，不是版本号。**

### 1.1 一句话边界

| 项 | 结论 |
| :--- | :--- |
| 建模对象 | 中国民事法律受控子领域；规范、要件、事实、效果、主体五模块 |
| 推理骨架 | 演绎涵摄为主，类比与归纳作为显式通道（非绕行） |
| 事实源 | `ontology/` 下的 Turtle 文件，**唯一真值** |
| 生成物 | `wiki/`、`retrieval/`、`vis/`，人改无效（重跑即覆盖） |
| 不做什么 | 不导入现成法律本体、不凭记忆写法条、不把系统推理标为「已验证」 |

## 3. 建模架构

### 3.1 五模块与四层元设计

概念层按**法律推理的角色**切分，而非按部门法切分。这样切的收益是：规则、要件、事实之间的连接关系在结构上可判定，不必依赖自然语言标签。

| 模块 | 承载 | 首批概念数 |
| :--- | :--- | ---: |
| **主体模块** | 谁——权利主体、义务主体、特殊身份主体 | 311 |
| **关系模块** | 何关系——权利义务的关联形态 | 83 |
| **规范模块** | 依何规范——规则、原则、条文 | 1 |
| **行为模块** | 做什么——法律行为、事实行为 | 22 |
| **效果模块** | 产生何效果——权利变动、责任承担 | 22 |
| （待裁定） | 两种归类皆可自圆其说，交负责人判断 | 6 |

> 规范模块仅 1 条，是因为概念层首批素材以「名词清单」为主，动词与规范形态集中在后续批次。这不是分布失衡，而是本轮素材的边界。

### 3.2 tbox 文件分工

```text
00-namespace.ttl     命名空间与通用词汇
10-module.ttl        五模块骨架（46 行，最薄的一层）
20-norm.ttl          规范层：规则、要件、效果、模态、可废止性
30-fact.ttl          事实层：因子、关键事实、证据关联
40-case.ttl          案例层：判决、争点、裁判要旨
50-application.ttl   涵摄层：规则适用、要件满足判定
60-states.ttl        状态轴：判断状态、溯源状态、置信、版本
70-concept-metadata.ttl  概念元数据模式
71-concepts-civil-code.ttl  民法典概念骨架（4 项生成参数见文件头）
```

**`71` 是生成物，不是手写文件**——由 `tools/import/import_civil_code.py` 从负责人投递的两份材料生成，生成参数（释义哈希 / 主体清单哈希）写在文件头。手改该文件会在下一次生成时被覆盖，且违反 `AGENTS.md` 禁止事项 3 的同类纪律。

### 3.3 三种推理的建设时序

演绎优先（`ADR-0010`）。原因不是演绎更「正确」，而是演绎的合法性条件最容易形式化——要件齐备、效果明确、无冲突，这些都可判定。类比与归纳的合法性条件是「相似点是否足以支持迁移」「反例是否足以否定」，属于法律实质判断，必须先有裁定通道（`ESC`）才能建模，否则会退化为系统替法官下结论。

## 4. 数据规模

### 4.1 概念层状态分布

| 判断状态 | 数量 | 含义 |
| :--- | ---: | :--- |
| `状态-候选` | 439 | 有投递材料支撑，等待逐条复核 |
| `状态-待裁定` | 6 | 模块归属两种归类皆可自圆其说，`ESC-0004` 待裁 |
| `已验证` | **0** | 无权威材料，按纪律不得产生 |

待裁定的 6 个概念：`期间`、`诉讼时效`、`不可抗力`、`占有`、`善意取得`、`添附`。

这 6 条都不是生僻词，恰恰是最常用、因而最容易「想当然归类」的概念。系统把它们交出去，而不是选一个看起来合理的答案——这是本项目最需要理解的一条设计意图。

### 4.2 溯源

| 文件 | 内容 |
| :--- | :--- |
| `PROV-0001` | tbox 自举基线 |
| `PROV-0002` | 概念层首批导入（逐文件登记） |
| `PROV-0003` | 外部实践采纳后的基线 |
| `PROV-0004` | 换行规范化后的新基线（**当前生效**） |

指纹按 `ontology/tbox/*.ttl` **原始字节**计算 SHA-256。校验器取按文件名排序的最后一条 `law:指纹` 作为期望值，与实测值比对，不一致即报 `W-TBOX-DRIFT`。

> 当前全量指纹 `22ff6bd99c824cf5…`、概念层指纹 `46e380f625494f51…`。因指纹对字节敏感，仓库已加 `.gitattributes` 锁定 `eol=lf`，详见 `ADR-0016`。

## 5. 快速开始

```bash
# 依赖
python -m pip install rdflib pyshacl

# ① 门禁：0 错误才算通过（退出码非零即有问题）
python tools/validate/validate.py

# ② 反例检出：证明校验器真的拦得住（当前 6/6）
python tools/validate/validate.py --negative

# ③ 能力问题执行：3 通过 / 17 未实现
python tools/test/run_cq.py

# ④ CQ 自检：证明这 3 条查询真能检出违规（当前 3/3）
python tools/test/run_cq.py --selftest

# ⑤ 投影生成（wiki/ 与 retrieval/manifest.json）
python tools/sync/sync.py

# ⑥ 可视化（vis/index.html）
python tools/vis/render.py

# ⑦ 门禁逻辑自检（8 个组合）
python tools/sync/sync.py --check-gate

# 可选：含结构演练样本
python tools/validate/validate.py --include-fixtures
```

上面第 ①②③ 三条是**进入项目的标准动作**。改动 `ontology/` 后必须重跑 ①，结果非「0 错误 0 警告」不得声称阶段完成（`AGENTS.md` 禁止事项 8）。

投影与可视化只能由工具生成，手改无效——`wiki/`、`retrieval/`、`vis/` 均在 `AGENTS.md §2` 中标为不可写。

## 6. 质量门禁

### 6.1 三道门禁

| 门禁 | 命令 | 当前结果 | 作用 |
| :--- | :--- | :--- | :--- |
| 一致性校验 | `validate.py` | **0 错误 0 警告** | SHACL 形状 + 跨文档引用完整性 |
| 反例检出 | `validate.py --negative` | **6/6 = 100%** | 证明校验器不是空转 |
| 能力问题 | `run_cq.py` | 3 通过 / 17 未实现 | 已执行项 3/3，覆盖率 15% |

**「0 警告」是开箱可复现的**：全新克隆后 `tbox 指纹` 与登记值一致，无需额外配置（`ADR-0016`）。

### 6.2 反例检出：校验器有效性的证据

一个从未拦截过任何错误的校验器，和一个从未运行过的校验器，在报告上看起来完全一样。因此本项目准备了 6 份**人工构造的错误样本**，逐条验证校验器能否拦截：

| 样本 | 预期拦截 | 结果 |
| :--- | :--- | :---: |
| `BAD-01-rule-missing-effect` | `E-RULE-02` | ✅ |
| `BAD-02-concept-two-modules` | `E-TAX-02` | ✅ |
| `BAD-03-subclass-cycle` | `E-TAX-01` | ✅ |
| `BAD-04-verified-selfdesign` | `E-PROV-01` | ✅ |
| `BAD-05-broken-chain` | `E-CHAIN-01` | ✅ |
| `BAD-06-term-class-and-property` | `E-TERM-02` | ✅ |

检出率 6/6。其中 `BAD-04` 值得单说：它构造的是「系统自身设计却标 `已验证`」——这条错误不是格式问题，而是**认知越界**，校验器把它拦下来，意味着「不得自我认证」这条纪律是可执行的，不只是文档承诺。

### 6.3 CQ 覆盖现状

20 条能力问题中 3 条已实现（`CQ-D02` 要件标注齐全、`CQ-I02` 候选规则与成文规则同构、`CQ-M03` 无「已验证+自建设计」组合），17 条**显式标注未实现**。

未实现项计入覆盖率分母、不计入通过率分子。这是刻意的：空转不是通过（`ADR-0013 §2.7`）。把 17 条未实现藏起来，覆盖率就能写成 100%，但那个数字没有意义。

## 8. 治理机制

本项目的治理成本高于一般代码项目，原因是：**本体的错误是沉默的**。代码写错会崩，本体写错不会——它会安静地被下游检索、被未来的推理引用。因此每类事件对应固定记录，不靠自觉。

### 8.1 记录类型

| 类型 | 触发事件 | 数量 |
| :--- | :--- | ---: |
| `ADR` | 任何选择，含放弃方案 | 16 |
| `LOG` | 每次执行结束 | 9 |
| `RSK` | 任何未决问题 | 9 |
| `ESC` | 无法裁定的法律判断 | 4 |
| `CON` | 任何概念/结构变更 | 2 |
| `ITER` | 每轮完整闭环 | 1 |
| `META` | 每阶段结束 | 1 |

### 8.2 三条不可让渡的纪律

1. **记录先于实现**——改 `ontology/` 前必须有 ADR 或 CON。
2. **不确定就停**——法律实质判断无 `verified` 支撑时，唯一合法动作是写 `ESC` 并把节点置 `待裁定`。「猜一个再标候选」不是可接受的替代方案。
3. **事实源唯一**——`wiki/`、`retrieval/`、`vis/` 上发现的不一致，全部回到 `ontology/` 修复。

### 8.3 命名空间（与项目名不一致，为有意保留）

术语 IRI 基础命名空间为 `https://ontology.law-cn.internal/mcl#`，前缀 `law:`。

项目名为 CLIO，该命名空间**未随之迁移**，是决策而非疏漏（`ADR-0014 §2.3`）：改项目名改变的是称呼；改 IRI 会使全部 445 个概念、77 个属性成为图层面上的另一批实体，属**破坏性变更**，须独立 ADR 处理，并同步 `owl:priorVersion`、旧 IRI 保留期、445 份投影重生成与指纹重登记。该迁移登记于 `RSK-0009`。

`.internal` 域不可解析，故当前 IRI 不能解引用取定义——本项目尚无对外发布地址，所有使用均以本地 `ontology/` 文件为输入。
